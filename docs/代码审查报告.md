| 级别 | 数量 | 实际后果 |

## 二、P0 阻断

### P0-1 `ssl.https` 发不了 `http://`，本地模型与自建网关全挂

**证据**

```lua
-- ajbk_net.lua:114-127
--- 发 HTTPS/HTTP 请求。返回 ok, code, content；   ← 注释声称支持 HTTP
local function httpRequest(headers, url, body, block_timeout, total_timeout)
    local https = require("ssl.https")             -- :119
    ...
    local req_ok, code_or_err = https.request{     -- :122
```

LuaSec 的 `https.lua` 对 `request` 无条件做 `url.create = tcp`（强制 TLS 握手），端口缺省补 443，**不看 URL 的 scheme**；按 scheme 派发是上游 LuaSocket `http.lua` 的职责（`SCHEMES[nreqt.scheme].create`，缺 scheme 时默认 http）。KOReader 自己的 `socketutil.lua` 注释把这点写得很明白：

> LuaSocket's adjustrequest function (in http.lua) passes the adjusted nreqt table to it, **but only when it does the automagic scheme handling**, not when it's set by the caller :/

KOReader 所有联网模块（`wikipedia.lua:147`、`translator.lua:506`、`otamanager.lua:114`）统一用 `socket.http.request`，就是因为它能按 scheme 自动分派 http/https。

**影响**：`presets.lua:108` Ollama（`http://localhost:11434/v1`）、`presets.lua:114` LM Studio（`http://localhost:1234/v1`），以及用户在"修改 API 地址"里填的任何 `http://` 局域网地址，全部会以 TLS 握手失败告终，界面上只显示 `网络请求失败：...`。这两个预设是"本地跑模型、不花钱、不出网"的主要卖点，等于直接废掉。

**修复**：换 `socket.http.request`（KOReader 里 http/https 通吃），顺带把 User-Agent 也接上。

```lua
local http = require("socket.http")
...
local req_ok, code_or_err = http.request{ ... }  -- 其余参数不变
```

**附带收益**：`socketutil.lua` 会把 KOReader 的 UA monkey-patch 进 `http.USERAGENT`，而 `ssl.https` 这条路径拿不到——换过去之后请求头也合规了（部分网关/WAF 会因此拒掉裸请求）。

**30 秒自验**：桌面上 `luajit -e 'local h=require("ssl.https") print(h.request{url="http://localhost:11434/v1/models", sink=require("ltn12").sink.table({})})'` 应当报握手失败；把 `ssl.https` 换成 `socket.http` 后同一句能拿到 200 或连接拒绝（而不是 TLS 错误）。

## 三、P1 高危

### P1-1 API Key 输入框是明文（`input_type` 不是密码开关）

**证据**：`main.lua:416` 与 `main.lua:510` 都写 `input_type = "password"`。

```lua
-- inputtext.lua:26-27
input_type = nil,  -- "number" or anything else
text_type = nil,   -- "password" or anything else
```

`input_type` 只用来切数字键盘（`inputtext.lua:558`、`:760`）；密码掩码走 `text_type`（`inputtext.lua:568` `self.is_password_type = self.text_type == "password"`，`:633` 掩码渲染，`:585-599` 还自带"显示/隐藏"眼睛按钮）。`InputDialog` 透传的是 `text_type = self.text_type`（`inputdialog.lua:383`），`MultiInputDialog` 也一样透传 `text_type = field.text_type`（`multiinputdialog.lua:139-143`）——两边都支持，只是字段名写错了。

**影响**：填 Key 时密钥在电纸书屏幕上明文显示，旁人一眼看全。讽刺的是自家 `docs/技术调研.md:267` 写的正是 `text_type="password"`——**代码和自己的设计文档相悖**。

**修复**：两处 `input_type = "password"` → `text_type = "password"`。

### P1-2 配置放插件目录，升级插件即丢 API Key

**证据**：`main.lua:57-60`

```lua
AjkbSettings.setConfigPath(self.path .. "/" .. CONFIG_FILENAME)
self.settings_file = AjbkSettings.getConfigPath()
```

配置落在 `AJBK.koplugin/ajbk_config.lua`。KOReader 的"删除插件"走 `ffiUtil.purgeDir(plugin.path)`，整目录删除；用户升级插件的常规做法（删旧目录、解压新目录）同样是整目录替换。`pluginloader.lua` 的 `deletePluginSettings` 也只认 `instance.settings_file`（`.old` 备份一并删）——作者显然权衡过"删除插件即无残留"，`README.md:20` 也把它当卖点写了。

**影响**：升级一次，19 家预设外所有自定义提供商、每家已填的 Key、自定义提示词、思考档位**全部归零**，用户只会看到"怎么又要填 Key"。这是用户投诉概率最高的行为，而它是"设计选择"而非疏忽，所以更值得改。

另外，插件目录若只读（`README.md:125` 已知会失败），`LuaSettings:flush()` → `util.writeToFile` 会 `logger.warn` 后返回 false，**不抛异常**；插件又把返回值丢了（`ajbk_settings.lua:54-56`），于是"保存"按钮永远成功、配置永远不落地。用户无感知，比报错更难查。

**建议**：配置移到 `DataStorage:getSettingsDir() .. "/ajbk.lua"`（KOReader 升级/重装插件都不会碰它），"删除即无残留"改由插件自己的"清除配置"菜单项提供；至少要把 `save()` 的失败反馈到 UI。

### P1-3 多行 `<think>` 块剥不掉，且可能把正文一起吃光

**证据**：`ajbk_net.lua:76-77`

```lua
text = text:gsub("<think>.-</think>", "")
text = text:gsub("<think>.*$", "")
```

Lua 模式里 `.` 不匹配换行。主流思考模型（Qwen3、DeepSeek-R1 蒸馏、各类本地模型的 `enable_thinking`）输出的思考块**几乎总是多行**：

```
<think>
用户想查"龘"...
</think>
龘，dá，龙腾飞的样子。
```

第一条 gsub 匹配不到任何东西；第二条 `<think>.*$` 只能吃到第一行（`<think>` 后面紧跟换行，`.*` 匹配空），于是把 `<think>` 这行删掉，**思考内容原样留在释义里**。反过来，如果模板是 `<think>用户…` 单行开头、正文在下一行的形式，第二条 gsub 会把开头到行尾吃掉——展示效果取决于模型排版，属于"随机泄漏"。测试里 `postProcess` 的 6 个用例（`tests/ajbk_test.py:157-162`）全是单行样本，正好躲过。

**修复**：别再用 `.` 硬碰换行，直接逐行扫（`gmatch("(.-)\n")` 的写法在 Lua 里不牵扯模式转义，也顺带处理了未闭合块）：

```lua
local out, in_think = {}, false
for line in (text .. "\n"):gmatch("(.-)\n") do
    if line:find("<think>", 1, true) then in_think = true end
    if not in_think then out[#out + 1] = line end
    if line:find("</think>", 1, true) then in_think = false end
end
text = table.concat(out, "\n")
```

若坚持正则，LuaJIT 下可用 `<think>[%z\1-\255]-</think>`（`%z` 匹配 `\0`，`\1-\255` 覆盖全部字节，含 `\n`），但可读性差，不推荐。

同时补两条测试：多行闭合块、未闭合块 + 后续正文。

## 四、P2 中等

### P2-1 postProcess 之后是空串，仍然当成功返回

`ajbk_net.lua:200` 直接 `return true, AjbkNet.postProcess(out)`。若模型只回了 `**龘**` 这种被 `%*%*` 剥光的、或只回了一个 `<think>` 块，postProcess 结果是 `""`，`chatCompletion` 报成功，`queryWord` 走 `showResult` 渲染一个空白查询窗——用户看到"窗口弹出来了但什么都没有"，排查成本很高。

**修复**：`local cleaned = postProcess(out); if cleaned == "" then return false, T("模型返回了空内容，请重试或更换模型。") end; return true, cleaned`。

顺带一个同源的坑：`main.lua:185` 的失败分支没兜底 `content`。子进程里若发生未捕获异常（`chatCompletion` 本身防御得挺严，但 `provider.base_url` 为 nil 时 `joinURL` 直接 `attempt to index a nil value`），子进程不会写出任何序列化结果，`dismissableRunInSubprocess` 只返回 `completed`，于是 `ok`、`content` 双双为 nil，用户看到 `AJBK 查询失败：nil`。建议写 `content or _("未知错误")`。

### P2-2 总超时是摆设：`ltn12.sink.table` 不执行 total_timeout

`ajbk_net.lua:121-127` 设了 `CHAT_TOTAL_TIMEOUT=90` / `MODELS_TOTAL_TIMEOUT=30`，但 sink 用的是 `ltn12.sink.table`。KOReader 的 `socketutil` 注释原话：

> In our case, we want to enforce an *actual* limit on how much time we're willing to block for, start to finish. **We do that via the custom sinks below.**

`socketutil:set_timeout` 设的是 socket 层超时（每次读取重置），真正的总时长靠 `socketutil.table_sink(t)` / `file_sink`。所以现在"90 秒总超时"不存在，只剩"单次阻塞 60 秒"；服务器挤牙膏式回包时，UI 会被吊住远超 90 秒。

**修复**：`sink = socketutil.table_sink(sink_tbl)`（返回的 `f, t`，取第一个即可），`reset_timeout()` 之后再用 `socketutil.describe_error(code, block, total)` 把 `timeout`/`wantread`/`sink timeout` 翻成人话——现在是把原始错误码（如 `wantread`）直接怼给用户看（`ajbk_net.lua:131`、`:178`）。

### P2-3 设置菜单保存后不刷新（父菜单留旧值）

`touchmenu.lua:868-917` 的规则：只有带 `checked/checked_func` 的项，回调后自动 `updateItems()`；`text_func` 项不会。

- `main.lua:298-304`"添加自定义提供商"的 callback 不接收 `touchmenu`，添加成功后不刷新 → 新提供商在退回到这一层菜单前一直不显示，用户以为没加上（只有一闪而过的"已添加"）。
- `main.lua:650-684`"手动输入模型名"保存后，上一层的"当前模型：X"仍是旧值（这一项是纯 `text_func`，不在自动刷新之列）。
- `main.lua:626-648` 模型列表里选定后，父菜单的"当前模型"同样不刷新。这条链路更绕（`fetchAndShowModels` 经 `runWhenOnline` 异步走），需要把 `touchmenu` 一路传进 `showModelListDialog`，选中并 `close(model_menu)` 之后再 `touchmenu:updateItems()`；`keep_menu_open = true` 保证父菜单那时仍活着。
- 改 Key / 改地址（`main.lua:410-447`、`:449-491`）不影响任何菜单文案，无需处理；但 `:470` 的"测试"用的是**已保存**的 Key 搭配**输入框里**的地址，改地址又改 Key 的场景下会测到半新半旧的组合——知道即可。

**修复**：给 `showAddCustomProviderDialog(touchmenu)` / `showManualModelDialog(touchmenu)` 加参数，保存分支末尾 `if touchmenu then touchmenu:updateItems() end`（`addPresetProvider` 已经是这么写的，`main.lua:401-403`，照着抄即可）；模型列表那条把 `touchmenu` 顺着 `fetchAndShowModels(p, touchmenu)` → `showModelListDialog(p, models, touchmenu)` 传下去。

### P2-4 `workflow_dispatch` 这条路径是坏的

`release.yml:38-40` 用 `GITHUB_REF_NAME` 当版本号、`:49-54` 用 `action-gh-release` 且不传 `tag_name`：

- 手动触发时 `ref_name` 是分支名（`main`），`_meta.lua` 版本会被写成 `version = "main"`；
- `action-gh-release` 在非 tag 的 ref 上会直接失败（"GitHub Releases requires a tag"）。

`permissions: contents: write` 已在 `:19-20` 声明，403 那条不用担心。

**修复**：要么把 `workflow_dispatch` 删掉（只走 tag），要么加 `inputs.version` 并显式 `tag_name: v${{ inputs.version }}`。顺带一句：`pip install lupa` 没锁版本（`:30`），某天 lupa 发新版把 CI 弄红纯属自找。

### P2-5 测试桩自己就是个 bug

`tests/ajbk_test.py:40` 的 `template` 桩：

```python
return out.gsub("%" .. i, tostring(v))   -- 生成模式 "%1"
```

Lua 里 `%1` 是"第 1 个捕获组"的引用，`string.gsub` 会报 `invalid capture index`；而真实模板函数是按**字面量** `%1` 匹配的（模式里必须写成 `%%1` 或 `%%(%d+)`）。现在 34 项测试全绿，只因为**没有任何一条路径真的调用了 `T()`**——一旦有人给 `_()` 文案加个 `%1` 的用例，测试会以极其误导的报错炸掉。

**修复**：`out.replace("%" + str(i), str(v))`（不解释为正则）。
